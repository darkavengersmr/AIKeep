# Постановка задачи
## 1\. Цель проекта
Необходимо спроектировать и подготовить план реализации веб-приложения для создания и управления заметками и списками дел.

Приложение по базовому функционалу должно быть аналогично Google Keep, но с обязательной поддержкой совместных списков дел между несколькими пользователями.

Основной результат работы на данном этапе — детальный план реализации проекта, включающий:

- предлагаемую архитектуру;
- выбор технологий;
- структуру frontend и backend;
- схему базы данных;
- модель авторизации и регистрации;
- описание основных сущностей;
- API или другой механизм взаимодействия frontend/backend;
- модель совместного доступа;
- этапы разработки;
- декомпозицию на конкретные задачи;
- выявление технических рисков и спорных мест.

Необходимо сначала составить план реализации, а не сразу писать код.

# 2\. Технологический стек
## Основной вариант
Предлагаемый стек:
### Frontend
- Next.js;
- React;
- TypeScript.
### База данных
- PostgreSQL.
### Backend
Предпочтительно использовать возможности Next.js для backend-части:

- Route Handlers;
- Server Actions, где это уместно;
- серверную бизнес-логику Next.js.

Если в процессе проектирования будет сделан вывод, что для приложения с совместной работой, авторизацией и потенциальным realtime-функционалом возможностей Next.js недостаточно или архитектура станет неоправданно сложной, допускается отдельный backend на:

- Nest.js;
- TypeScript.

При выборе Nest.js необходимо обосновать, почему отдельный backend предпочтительнее.

# 3\. Общая концепция приложения
Пользователь после авторизации получает доступ к личному пространству, где может:

- создавать заметки;
- редактировать заметки;
- удалять заметки;
- создавать списки дел;
- отмечать задачи как выполненные;
- организовывать и просматривать свои материалы;
- предоставлять другим пользователям доступ к определенным спискам дел.

Необходимо разделить понятия:

1. Личные данные пользователя.
1. Совместно используемые данные, к которым имеют доступ несколько пользователей.

# 4\. Авторизация и регистрация
## 4\.1. Регистрация
Регистрация нового пользователя должна быть возможна только при наличии секретного кода-приглашения.

Предполагаемый сценарий:

1. Пользователь открывает страницу регистрации.
1. Вводит:
   1. имя или отображаемое имя;
   1. email;
   1. пароль;
   1. секретный код-приглашение.
1. Система проверяет код.
1. Если код действителен, создается пользователь.
1. Пользователь получает возможность авторизоваться или автоматически входит в систему.

Необходимо предусмотреть модель кодов-приглашений.

Для кодов желательно поддержать следующие возможности:

- уникальный код;
- возможность включить/отключить код;
- ограничение количества использований;
- срок действия;
- информация о количестве использований;
- возможность создания новых кодов в будущем.

Нужно определить, требуется ли отдельная административная роль для управления приглашениями.

## 4\.2. Авторизация
Необходимо реализовать стандартную авторизацию пользователей.

Минимально:

- вход по email и паролю;
- безопасное хранение паролей;
- поддержка пользовательской сессии;
- выход из системы;
- защита приватных маршрутов.

Предложить подходящий механизм авторизации для выбранного стека.

# 5\. Пользователи
Для каждого пользователя необходимо предусмотреть:

- уникальный идентификатор;
- email;
- пароль в безопасном виде;
- отображаемое имя;
- дату создания;
- дату последнего изменения.

В будущем архитектура должна позволять расширять профиль пользователя без серьезной переработки системы.

# 6\. Заметки
Приложение должно поддерживать базовую функциональность заметок, аналогичную Google Keep.
## 6\.1. Создание заметки
Пользователь должен иметь возможность создать заметку со следующими полями:

- заголовок;
- текстовое содержимое;
- цвет или визуальная категория;
- дата создания;
- дата последнего изменения.

## 6\.2. Редактирование
Пользователь должен иметь возможность:

- изменить заголовок;
- изменить содержимое;
- изменить цвет;
- сохранить изменения.

## 6\.3. Удаление
Необходимо определить оптимальную модель удаления:

- физическое удаление;
- мягкое удаление (soft delete);
- корзина с возможностью восстановления.

Предпочтительно предусмотреть архитектуру, позволяющую в будущем реализовать корзину.

## 6\.4. Дополнительные возможности
На этапе проектирования предусмотреть возможность дальнейшего добавления:

- закрепления заметок;
- тегов;
- архивирования;
- поиска;
- фильтрации;
- напоминаний;
- прикрепления файлов или изображений.

Не обязательно реализовывать все эти функции в первой версии, но архитектура не должна препятствовать их добавлению.

# 7\. Списки дел
Пользователь должен иметь возможность создавать списки дел.

Пример:

Покупки

- Купить молоко
- Купить хлеб
- Купить овощи

Каждый элемент списка должен иметь как минимум:

- уникальный идентификатор;
- текст задачи;
- статус выполнения;
- порядок отображения;
- дату создания;
- дату изменения.

Пользователь должен иметь возможность:

- добавлять пункты;
- редактировать пункты;
- удалять пункты;
- отмечать пункты выполненными;
- менять порядок пунктов.

# 8\. Совместные списки дел — обязательная функция
Это одна из ключевых функций приложения.

Необходимо реализовать возможность предоставлять нескольким пользователям доступ к одному списку дел.

Пример:

Пользователь A создает список:

Совместные покупки

После этого он добавляет пользователей B и C.

Все пользователи получают доступ к одному и тому же списку.

## 8\.1. Совместный доступ
Необходимо предусмотреть роли участников списка.

Минимальный набор:
### Owner
Создатель списка.

Может:

- редактировать список;
- добавлять участников;
- удалять участников;
- удалять список;
- передавать права владельца, если это будет поддержано.
### Editor
Может:

- просматривать список;
- добавлять задачи;
- редактировать задачи;
- отмечать задачи выполненными;
- удалять задачи.
### Viewer
Может:

- просматривать список;
- видеть изменения других пользователей.

В первой версии можно реализовать только Owner и Editor, если это существенно упростит MVP, но архитектура должна позволять добавить Viewer.

## 8\.2. Добавление участников
Необходимо определить удобный сценарий добавления пользователя в совместный список.

Возможные варианты:

- поиск пользователя по email;
- приглашение по email;
- приглашение по внутреннему идентификатору;
- ссылка-приглашение.

Для MVP предпочтительно выбрать наиболее простой и безопасный вариант.

# 9\. Синхронизация изменений
Необходимо определить требования к синхронизации совместных списков.

Минимальный вариант:

- изменения сохраняются в базе данных;
- при следующем обновлении страницы другой пользователь видит актуальные данные.

Желательный вариант:

- изменения появляются у других участников автоматически или почти автоматически;
- используется realtime-механизм, например:
  - WebSocket;
  - Server-Sent Events;
  - polling;
  - другой подход.

Необходимо отдельно оценить:

1. Нужен ли realtime в MVP.
1. Насколько сложно реализовать его в Next.js.
1. Имеет ли смысл использовать Nest.js для WebSocket/realtime.

Если realtime не входит в первую версию, необходимо спроектировать систему так, чтобы его можно было добавить позже.

# 10\. Права доступа
Необходимо обеспечить строгую проверку прав доступа на backend.

Важно:

- пользователь не должен получать доступ к чужим личным заметкам;
- пользователь должен получать доступ к совместному списку только при наличии соответствующего разрешения;
- нельзя полагаться только на ограничения frontend;
- каждая операция изменения данных должна проверять права пользователя.

Необходимо описать модель авторизации и проверки доступа для:

- заметок;
- списков;
- элементов списков;
- участников совместных списков.

# 17\. Принципы принятия решений
При подготовке плана необходимо придерживаться следующих принципов:

1. Сначала ориентироваться на простой и качественный MVP.
1. Не усложнять архитектуру без необходимости.
1. Предпочитать Next.js-only архитектуру, если она достаточно надежна для требований.
1. Использовать Nest.js только при реальной архитектурной необходимости.
1. Совместные списки должны быть полноценной частью модели данных, а не временным решением.
1. Все права доступа должны проверяться на сервере.
1. Архитектура должна позволять дальнейшее развитие приложения.
1. План должен быть достаточно подробным, чтобы после него можно было последовательно переходить к реализации.
